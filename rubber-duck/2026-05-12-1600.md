## Rubric Evaluation And Prefab Response Workflow

The discussion began with debugging a rubric-driven response workflow.
The current system judges whether a response is specific enough, then
falls through to a prefab message such as "that did not work." In the
example discussed, this was misleading because no code had actually
been run. The issue was not that a student fix had failed, but that
the evaluator decided the guidance was not clear enough.

The preferred workflow is to let the question-answering step run
first, then use prefab messages only as glue between steps. The team
also discussed adding structured evaluator reasoning so local
debugging can show why the evaluator made a decision. A possible
structure is:

- analysis of the situation
- reasoning about how the rubric applies
- conclusion as a true or false decision

This should make it easier to debug the rubric and prompt, and may
improve the evaluator's decisions.

### Designs Discussed

One design is a two-step evaluation process. First, a step explicitly
thinks through evidence that a rubric item applies or does not apply.
Second, a conclusion step decides whether the response is acceptable
given those observations. This gives the workflow structured thought
instead of relying on the model to infer the important considerations.

Another design is to build a large curated list of prefab messages and
have the agent select the best one for the situation. This would
reduce response leakage because the final student-facing text is
selected from approved phrases. The agent should still reason about
the situation, and logging should record why a phrase was selected.

### Decisions

- Prefab messages should be used after conversational steps, not as a
  substitute for evaluating or trying the current step.
- Evaluator output should include reasoning that can be inspected
  during local debugging.
- The large-prefab-list approach is worth trying.

## Scenario Documentation And Application Interface Design

The application interface document has grown instead of becoming a
smaller index. The preferred direction is for it to explain why it
exists, reference the application scenarios philosophy or skill name,
and then act as an index into scenario areas. It should not try to
duplicate scenario detail.

The docs currently mix stable documentation with agent working space.
Plans and spring-cleaning files are intermediate agent artifacts,
while scenarios and application interface docs are stable application
documentation. These should be separated. A possible new location for
agent working files is `agent-scratch/`.

The team discussed how scenarios should be written. A scenario should
describe observable behavior and expectations, not implementation
details that will drift. When a scenario is too specific about current
configuration structure or implementation, the scenario workflow
should catch that during review.

### Designs Discussed

Scenarios should include context, motivation, proposed behavior, and
concrete examples. For configuration behavior, this means showing the
developer-facing YAML that someone would write and explaining what
that syntax means. For CLI behavior, it means showing commands and
expected results. For chatbot behavior, it means showing concrete
conversation examples or case studies.

Scenarios were compared to Python Enhancement Proposals. A good
scenario should have some of the same rigor: rationale, terminology,
examples, exceptional cases, and a clear description of the desired
world. Unlike PEPs, scenarios should describe the current state of the
application rather than remain as historical diffs.

The "brush stroke" model was introduced. A scenario does not need to
cover an entire end-to-end feature. Each scenario can describe one
part of the application behavior. Together, the scenario set forms the
current documentation for the application.

### Decisions

- `application_interface.md` should become a compact index into
  scenario areas, with a short explanation of the scenario philosophy.
- Agent working artifacts such as plans and spring cleanings should be
  separated from stable docs.
- Agent working artifacts should live under `agent-scratch/`.
- Scenarios should focus on observable behavior and user expectations.
- Scenario examples should include concrete interface examples where
  relevant, such as YAML, CLI commands, and conversation snippets.
- Existing scenarios should describe the current application behavior.
  New work may update existing scenarios or add new ones.

## Scenario Workflow Strategy For Myteam And Rubber Duck

Two distinct scenario workflows were identified. The first is a
temporary workflow for existing applications that do not yet have
scenarios. It should help generate scenario documentation from the
current codebase. The second is the ongoing workflow for new work,
where scenarios are added or updated before implementation.

The existing-application workflow should focus on observable behavior.
It should ask the agent to explain how the application behaves and how
a human uses it, rather than focusing on implementation details. That
conversation can then be postprocessed into scenario brush strokes and
tests.

the scenario-generation approach. After that works, the team can apply
the process to rubber duck.

## Script Prompt Placement

The final topic was where to put prompts used by support scripts such
as the river-size script. The existing `scripts` folder currently has
one script and the docs are tailored to that script. The `prompts`
folder is intended for production prompts that support the system, and
prompts should be treated as source code.

For small, script-specific prompts, the preferred approach is to embed
the prompt in the script as a multi-line string so the script stays
self-contained. If the prompt grows large or the script needs more
supporting files, it can become a folder with separate prompt files.

### Decisions

- Production prompts should live with source code rather than as loose
  top-level files.
- The existing top-level `prompts` folder should generally move under
  source code.
- Simple script-specific prompts can be embedded directly in the
  script.
- Larger script prompt systems can be split into a folder later.
