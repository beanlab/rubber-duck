# Debugging Practice Response Flow

## Summary

The debugging practice is mostly functioning as intended, but the
handling of incorrect or confused student answers still needs work.
The main problem is topicality: when a CS 110 student does not
understand an error, broad suggestions such as "look up syntax
errors" are not useful and can send the student into material that
is too general or too advanced.

The specific example discussed was a prompt call where the student
left off quotation marks around a string literal. Python then
interprets the input as multiple tokens instead of a quoted string,
producing a syntax error. The current fallback response points the
student toward how Python handles arguments, but that still feels
indirect.

## Designs Discussed

The group considered sending students to a guide entry or a TA when
the duck cannot give a useful non-leading response. One possible
design is to index guide entries, choose the most relevant entry for
the error, and direct the student there. Another option is to avoid
errors that are hard for the duck to handle. That was rejected as
incomplete because rare student mistakes still occur and are worth
supporting.

The preferred debugging flow should ask for four pieces, in order:

1. What is the error?
2. Where did it happen?
3. What was supposed to happen at that location?
4. How do you make that happen?

If the student skips ahead, proposes a fix without explaining the
error, or goes off topic, the duck should redirect them to the next
missing step. For example, before asking how to fix a `NameError`,
the duck should first ask what a `NameError` means, then where it
happened, then what the code intended at that location.

The prompt shown to students should ask directly what the error
means. If the student has not identified where the error occurs,
the duck should ask for the location before asking for a concrete
code change. If the student has already covered the location, the
duck can move to the fix.

Line numbering should be generated automatically rather than
produced by the rubric agent. The rubric agent should produce plain
code, and the workflow should prepend line numbers when storing or
displaying the code. Semicolons should be removed from the display
because they may confuse students; a pipe can be used as a visual
separator if needed.

## Decisions

- Use the four-step debugging sequence as the core response flow.
- Prompt the student first for what the error means.
- Redirect confused answers back to the traceback and relevant code.
- Generate line numbers outside the rubric agent.
- Remove semicolons from displayed code.

# Concept-Explanation Delegation

## Summary

The meeting identified a need for a narrow explanatory mode when the
student repeatedly does not understand the target concept. Instead
of deferring to external study resources, the system should
temporarily delegate to another duck whose only job is to explain
the specific concept blocking the student.

## Designs Discussed

The student should see one continuous conversation. Under the hood,
control can move to a different agent for a short period. That agent
receives the current context and a narrow objective, such as
explaining one syntax error or one `NameError`. It should not help
with unrelated homework or broaden the topic. If the student asks
off-topic questions, it should redirect back to the current concept.

When the explanation objective is complete, the delegated agent
should use a tool call or similar mechanism to end its loop and
return control to the assessment agent. Because the current
assessment flow manages context manually, the explanatory exchange
can appear in the shared conversation history.

The handoff should happen after the system has identified the
concept the student is missing. If the student is still guessing
randomly, the duck should first prompt them to inspect the traceback
and code location so the misunderstood concept can be identified.

There was also discussion of model choice for persona-heavy
behavior. Some open-source or hosted models may be less tuned toward
doing the work for the user and might follow educational personas
more naturally. This is worth exploring later, but the immediate
priority is the wiring and turn handling.

## Decisions

- Add a delegated explanation state for repeated conceptual
  confusion.
- Keep the delegated agent narrowly scoped to one concept.
- Return to the assessment flow after the explanation objective is
  met.
- Treat model exploration as a later option, not the immediate
  priority.

# Workflow Agent Adapter Design

## Summary

The `myteam` workflow agent adapter work moved from class-based
Codex and Pie backends to file-based adapters. Local overrides are
now supported in `.myteam`, so users can provide a `codex.py` file
to override built-in defaults. Pie support for session resumption is
also working.

## Designs Discussed

Each agent file now owns its own `get_session_id` function. Users
can inspect built-in agents as examples when creating custom
adapters. The Codex adapter currently includes executable handling,
an ID regex, `build_argv`, `get_session_id`, and input encoding
behavior.

The right-arrow and input-encoding behavior should likely move out
of agent-specific files and into workflow code. It is probably a
general workflow detail: paste the prompt, press the right arrow,
then press enter. If future agents need something more specialized,
the design can be revisited.

The built-in adapter files should include docstrings. `build_argv`
should explain that it creates the `Popen` argv, starts with the
executable, includes the prompt, and resumes a provided session ID.
`get_session_id` should explain that the nonce is a unique string
used to find the session for the current run.

Nonce handling needs to be strengthened. A new nonce should be
injected every time a session is started, resumed, viewed, or
forked, so session lookup cannot accidentally match a copied or
forked prior context. Resume should remain the default because it is
more efficient. Forking is useful when multiple agents need to
branch from the same context and perform different tasks.

The adapter should support interactive and non-interactive modes.
The recommended API is an `interactive` boolean, with Codex using
`--exec` when non-interactive. `build_argv` should also support
`model` and `extra_args`. `session_id`, `interactive`, and `model`
should be first-class parameters; `extra_args` can cover arbitrary
command-line flags.

The workflow runner was fixed so workflows run from the project root
rather than from inside `.myteam`. This fixes cases where Codex
could not find the project `.myteam` folder after running
`myteam get role`.

There was a cost and context discussion. Starting Codex and saying
`hi` used about 2.13K tokens, while loading `myteam get role` first
used about 18.1K tokens. Cached input affects actual cost, but
repeated startup and context growth still matter. This supports
resuming sessions where possible.

## Decisions

- Keep the file-based adapter approach.
- Move generic input encoding out of the Codex and Pie adapter
  files.
- Add docstrings to built-in adapter functions.
- Resume sessions by default; support forks for branching workflows.
- Add explicit support for `session_id`, `interactive`, `model`, and
  `extra_args`.
- Default `interactive` to true.
- Fork workflows when running simultaneous sessions.
- Support both resuming and forking sessions; generate a new nonce
  either way.
- Use the existing `agent` argument in `run_agent()` to switch
  workflow agents.
- Let local adapter overrides customize defaults rather than adding
  a separate configuration layer now.
