# Implementation Workflow Decomposition For Coding Tasks

## Summary

The team reviewed a new implementation workflow that decomposes a
coding task from `main()` into focused function-level work. The flow
finds the target file once, validates signatures, pops one unfilled
function at a time, and applies narrow instructions per function.

This approach was presented as successful on a complex CS 110 style
problem and seen as a strong base for larger automation.

## Designs Discussed

The discussed structure is top-down and iterative. The agent gets
task-specific guidance, decides whether to decompose, creates helper
functions only when needed, and returns the new function list plus
instructions scoped to each function.

A larger future flow was outlined for harder projects: architecture
analysis, package selection, architecture drafting, then parallel
implementation of independent functions.

## Decisions

- Keep the decomposition-first implementation workflow.
- Add the demonstrated workflow into `rosters` as reference.
- Continue testing on harder, class-like codebases.

# Workflow Session Control And Delegation Design

## Summary

The team discussed letting `myteam` start and suspend role sessions,
run a workflow as a temporary controlled sub-session, and then return
results to the original session. This would support cleaner
delegation and on-demand workflow execution during normal chat flow.

## Designs Discussed

The proposed model is a context handoff:
conversation context becomes workflow input, workflow steps run with
explicit objectives, then output returns to the parent session.

This allows a conversational agent to switch into a structured
implementation workflow only when needed.

## Decisions

- Pursue session suspension/resume patterns for cleaner delegation.
- Treat workflows as callable units during conversation.

# Prompting And Role-Loading Strategy In `myteam`

## Summary

The team questioned `AGENTS.md`-driven startup as default behavior.
The concern is repeated loading of broad instructions that are not
always needed. A leaner approach is to load only explicit role or
workflow context.

## Designs Discussed

The proposed change is `myteam start` with optional role loading and
fewer automatic reads. Prompt instructions stay in workflow code,
often as multi-line strings, with explicit outputs and error paths.

A practical pattern was shown: each step can fail fast with structured
error output when task fulfillment is not possible.

## Decisions

- Move toward explicit role/workflow loading over implicit
  `AGENTS.md` startup.
- Keep step prompts local to workflow definitions when practical.
- Preserve explicit error channels per workflow step.

# Model Cost Control And Usage Tracking

## Summary

Usage and cost were reviewed for the period from April 29 to
May 14, 2026. Reported totals were about one-third billion tokens and
$586 over two weeks, with most usage from two keys.

The group agreed current default model choices are too expensive for
routine work and discussed changing defaults plus better
instrumentation.

## Designs Discussed

Suggested controls included:
defaulting to `5.4-mini` or smaller models for routine steps,
using stronger models only for difficult steps, and compacting context
between logical phases to reduce token use.

Workflow-level usage tracking was identified as high value so each
step can report real cost during execution.

## Decisions

- Run `5.4-mini` as default for most work.
- Escalate to larger models only when needed per step.
- Continue using compaction between logical conversation phases.
- Prioritize workflow usage tracking implementation.

# Debugging-Practice Flow And Explanation Escalation

## Summary

The team reviewed an interactive debugging workflow and focused on
response quality for incorrect or partial student answers. The current
flow works but needs cleaner escalation and better handling of partial
correctness.

The reviewed examples centered on `NameError` and
`UnboundLocalError` interpretation and how much detail to require
before moving to the next step.

## Designs Discussed

A refined judge outcome was discussed with three classes:
correct, correct-but-incomplete, and incorrect. This enables targeted
follow-up prompts rather than repeated generic retries.

For escalated explanation mode, the team discussed giving the
explainer a concrete objective to end the loop:
identify the student's knowledge gap and record what explanation
resolved it, then return control.

## Decisions

- Prefer earlier explanation escalation after repeated incorrect
  answers (around two failed attempts).
- Add explicit handling for "correct but incomplete" responses.
- Use objective-based completion criteria for explanation subflows.
