# Teach-Me Rubber Duck Workflow

## Summary

The first development focus should be a new rubber duck mode where
students explain CS concepts to a duck that behaves like a learner.
The goal is not an oral exam. The student should act like a TA
teaching someone who knows less than they do.

The initial research question is whether an AI system can simulate a
learner well enough to help students articulate their understanding.
Likely first topics include `return`, variables, and similar concepts
that students often struggle with.

## Designs Discussed

The first version can avoid heavy anti-jailbreak hardening. Since the
conversations will be reviewed in PA review, misuse can be discovered
there and hardened later if needed.

The preferred architecture is a workflow with multiple model calls
under one apparent `run_agent` turn. A guardrail or assessment call
reads the conversation and evaluates:

- whether the student's explanation is correct
- which rubric points have not yet been covered
- whether anything said is inaccurate, unclear, or incomplete

A second call then crafts the next learner-like question. The
question should be posed innocently, such as asking for clarification
or saying the duck is confused, while still being guided by the
rubric and assessment.

The first iteration can ignore mistake detection and only assess
remaining rubric gaps. Once the plumbing works, prompt iteration can
build from there.

If a student reaches the limit of their knowledge, the preface should
tell them to step away and learn before continuing. Suggested support
paths include asking the standard Rubber Duck, asking a TA, or asking
a classmate, then returning to the teach-me duck once they have a
stronger working model.

Future ideas include switching between learner mode and explainer
mode, or using multiple duck personas. Those are not part of the
first implementation.

### Guidance

- Ask Codex to reason through the architecture, then
  evaluate whether the design feels simple and fits the codebase.
- Work with Ty on architecture questions before committing
  to a design.

## Decisions

- Start with a real multi-call workflow rather than a single prompt.
- Model the workflow after the user-led architecture.
- Expose the internal workflow as one apparent turn to the user.
- Start with GPT-5.4 mini and no reasoning.
- Add reasoning only after collecting examples that show it helps.
- Do not prioritize jailbreak hardening in the first pass.

# TTY Wrapper Architecture

## Summary

The TTY wrapper should be refactored toward a generator/context
manager design. A TTY session is naturally a stream of output with
input sent back in response. A generator models this well: it yields
output chunks and receives optional input through `.send()`.

## Designs Discussed

The proposed session shape is a generator that yields chunks of
terminal output. The caller handles each chunk, decides whether to
print it, swallow it, or respond, and sends input back when needed.

Cleanup is critical because the wrapper touches process state,
terminal state, signal handlers, and related operating-system
resources. A raw `finally` block can work, but the preferred Python
shape is a context manager used with `with`, so cleanup is guaranteed
and harder to forget.

The PTY session class should own mechanics:

- opening and closing the session
- streaming output chunks
- writing input
- restoring terminal state
- handling terminal size and signal concerns

The caller or runner should own interaction policy:

- whether a chunk is printed or hidden
- what initial input is sent
- what cues are watched for
- how the wrapper responds to those cues

Moving echoing and display decisions outside the PTY class enables
future behavior such as injecting a status command, reading and
parsing its output without displaying it, and rendering a separate UI
indicator.

Codex paste-burst behavior was also discussed. When input arrives
quickly, Codex may treat it as paste and treat newlines as content
rather than command submission. Ty found that sending content and the
newline separately made the workflow work. That is preferred over the
more complex right-arrow flush workaround if it remains reliable.

The design should avoid treating initial input as a special
client-specific command argument. Prefer one input path that works for
initial input and runtime input across clients.

## Decisions

- Refactor the wrapper around a generator-like session stream.
- Use a context manager to guarantee cleanup.
- Move display and echo decisions outside the PTY session mechanics.
- Prefer one general input path for both initial and runtime input.
- If separate content/newline sends work reliably, use that simpler
  approach.
